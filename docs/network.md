# Ограничение доступа VM к сети (vmguard)

Правила доступа задаются переменными окружения (или файлом) и применяются
**снаружи гостевой ОС** — внутри VM нет ни правил, ни агента, ни чего-либо, что
можно отключить из-под root.

Хосту дополнительные привилегии не нужны: ни `NET_ADMIN`, ни `/dev/net/tun`,
ни правил iptables/nftables на хосте. Только `/dev/kvm`, как и раньше.

---

## Как это работает

`qemux/qemu` в режиме `NETWORK=passt` запускает [passt](https://passt.top) —
сетевой стек в userspace. QEMU подключается к нему по unix-сокету и обменивается
ethernet-кадрами (4 байта длины в network order + сам кадр).

`vmguard` встраивается ровно в этот сокет:

```
 гость (QEMU)  ──►  vmguard  ──►  passt  ──►  сеть контейнера
                      │
                      └── кадр не прошёл ACL: TCP RST / ICMP prohibited обратно в гостя
```

Каждый кадр разбирается до IPv4/IPv6 + TCP/UDP/ICMP, сверяется со списком
правил, и либо пересылается дальше байт-в-байт, либо отбрасывается.

Почему именно так:

* **нельзя обойти изнутри** — гость видит только виртуальную сетевую карту;
* **не трогает хост** — никаких общих с другими контейнерами правил файрвола;
* **без привилегий** — всё происходит в userspace внутри контейнера;
* **не ломает NAT** — passt по-прежнему делает всю сетевую работу.

Ограничение: работает только при `NETWORK=passt` (значение по умолчанию в этих
образах). Если правила заданы, а режим сети другой — контейнер **не стартует** и
скажет почему. Молча работать без запрошенных ограничений он не будет.

## Быстрый старт

```yaml
services:
  ubuntu:
    image: ghcr.io/ophoperhpo/docker-vm-ubuntu-24.04:master
    devices: [ /dev/kvm ]
    volumes: [ ./storage:/storage ]
    environment:
      # VM ходит в интернет, но не видит домашнюю сеть и соседние контейнеры
      NET_PRESET: internet
```

Ничего больше включать не нужно: правила есть — фильтр работает.

## Пресеты

| `NET_PRESET` | Что получается |
|---|---|
| `open` (по умолчанию) | без ограничений |
| `internet` | всё, кроме приватных сетей (RFC1918, CGNAT, link-local, loopback, ULA) и cloud-metadata |
| `lan` | только приватные сети, интернета нет |
| `isolated` | ничего, кроме DHCP и DNS до шлюза |

Пресет применяется первым, ваши собственные правила — после него, поэтому его
можно точечно ослабить:

```yaml
environment:
  NET_PRESET: internet
  NET_ALLOW: 192.168.1.50:5432      # …но до этой БД в LAN ходить можно
```

## Синтаксис правил

```
[протокол:]цель[:порты]
```

| Часть | Значения |
|---|---|
| протокол | `tcp`, `udp`, `icmp`, `any` (по умолчанию — любой) |
| цель | IP, CIDR, имя хоста или алиас |
| порты | `443`, `80,443`, `8000-8100`, `*` |

IPv6 с портами пишется в скобках: `tcp:[2001:db8::/32]:443`.
Без портов скобки не нужны: `fd00::/8`.

Примеры:

```
10.0.0.0/8                  вся подсеть, любой протокол и порт
1.2.3.4                     один адрес
tcp:0.0.0.0/0:80,443        http и https куда угодно
udp:*:53                    DNS куда угодно
icmp:private                ping только по приватным сетям
tcp:api.github.com:443      по имени (резолвится и обновляется, см. ниже)
```

### Алиасы

| Алиас | Раскрывается в |
|---|---|
| `any`, `all`, `*` | `0.0.0.0/0` + `::/0` |
| `private`, `lan` | RFC1918 + `127/8` + `169.254/16` + `100.64/10` + `::1` + `fc00::/7` + `fe80::/10` |
| `rfc1918` | только `10/8`, `172.16/12`, `192.168/16` |
| `loopback` | `127/8`, `::1` |
| `link-local` | `169.254/16`, `fe80::/10` |
| `metadata` | `169.254.169.254`, `fd00:ec2::254` |
| `multicast` | `224/4`, `ff00::/8`, `255.255.255.255` |
| `gateway`, `host` | адрес шлюза, который passt показывает гостю |
| `guest` | адрес самой VM |
| `dns` | nameservers из `/etc/resolv.conf` контейнера |

## Переменные

| Переменная | Назначение |
|---|---|
| `NET_ALLOW` | список разрешающих правил |
| `NET_DENY` | список запрещающих правил |
| `NET_RULES` | упорядоченный список с явными глаголами: `allow:…` / `deny:…` |
| `NET_RULES_FILE` | путь к файлу с правилами (перечитывается на лету) |
| `NET_POLICY` | `allow` или `deny` — что делать, если ни одно правило не подошло |
| `NET_PRESET` | см. выше |
| `NET_BLOCK_PRIVATE` | `Y` — короткая запись для `NET_DENY: private` |
| `NET_ALLOW_IN` / `NET_DENY_IN` / `NET_RULES_IN` / `NET_POLICY_IN` | то же самое для входящих (матчится **адрес источника**) |
| `NET_GUARD` | `auto` (по умолчанию) / `Y` / `N` |
| `NET_GUARD_REJECT` | `Y` (по умолчанию) — отвечать RST/ICMP; `N` — молча дропать |
| `NET_GUARD_LOG` | `blocked` (по умолчанию) / `all` / `none` |
| `NET_GUARD_STRICT` | `Y` — отключить встроенные разрешения для DHCP/DNS/NDP |
| `NET_GUARD_STATEFUL` | `N` — не отслеживать соединения, проверять каждый пакет отдельно |
| `NET_GUARD_HTTP` | адрес HTTP-эндпоинта со статусом, например `:8010` |
| `NET_RESOLVE_INTERVAL` | как часто перерезолвить правила-имена (по умолчанию `60s`) |
| `NET_WATCHDOG` | `N` — не перезапускать контейнер, если passt/vmguard упал |

Списки разделяются запятыми, пробелами, точками с запятой или переводами строк —
как удобнее в compose. Запятая внутри списка портов не ломает разбор:
`tcp:10.0.0.1:80,443` — это одно правило.

### Порядок проверки

1. Встроенные разрешения: ARP, DHCP, DNS до шлюза, IPv6 neighbor discovery.
   Без них гость не получит адрес и не разрезолвит имена. Отключается через
   `NET_GUARD_STRICT=Y`. Подробности — [ниже](#встроенные-разрешения).
2. `NET_PRESET`
3. `NET_BLOCK_PRIVATE`
4. `NET_RULES_FILE`, затем `NET_RULES` — в том порядке, в котором написаны
5. `NET_DENY`
6. `NET_ALLOW`
7. `NET_POLICY`

Первое подошедшее правило решает. Если `NET_ALLOW` задан, а `NET_POLICY` — нет,
политика по умолчанию становится `deny`: перечислили, куда можно, значит
в остальные места нельзя.

## Встроенные разрешения

Все поля, на которые смотрят эти исключения, выбирает сам гость, поэтому каждое
описывает ровно тот обмен, ради которого существует. Правило вида «любой пакет
на порту 67 или 68» было бы дырой во всём ACL: достаточно взять такой исходящий
порт, чтобы уйти куда угодно.

| Исключение | Что именно разрешено |
|---|---|
| ARP | всё (без него линк не поднимется) |
| DHCPv4 | `68 → 67` на broadcast или шлюз, и ответ `67 → 68` от шлюза |
| DHCPv6 | `546 → 547` только в пределах линка (multicast, link-local, шлюз) |
| DNS | порт 53 **только** до шлюза и до nameservers контейнера |
| NDP / MLD | ICMPv6 типов 130–136 и 143 только на multicast, link-local или шлюз |

Всё остальное на этих портах — обычный трафик и проверяется правилами.
`NET_GUARD_STRICT=Y` убирает и эти исключения; тогда гостю нужно явно разрешить
DHCP и DNS правилами, иначе он не поднимет сеть.

### Непонятое — значит запрещено

passt разбирает кадр по ethertype и куда терпимее к тому, что за ним: он,
например, вообще не смотрит на поле version в IP-заголовке. Поэтому кадр,
который vmguard не смог разобрать, — это не «безобидный не-IP трафик», а пакет,
который passt вполне может доставить именно туда, куда правила запрещают.

Отсюда правило: **всё, что не разобралось, запрещается**.

| Кадр | Решение |
|---|---|
| ARP | пропускается (без него линк не поднимется) |
| IPv4/IPv6, разобран | проверяется правилами |
| IPv4/IPv6, не разобран (обрезанный заголовок, странная цепочка расширений) | запрещается |
| любой другой ethertype | запрещается (passt их всё равно не обрабатывает) |

По той же причине разбор намеренно повторяет passt там, где мог бы разойтись:
version в IP-заголовке не проверяется (как и у passt), а цепочка IPv6-расширений
следует только тем заголовкам, которые обе стороны читают одинаково; заголовок,
который passt интерпретирует иначе (50, 51, 139, 140, 253, 254), приводит к
запрету, а не к пакету, у которого vmguard и passt читают порт по разным
смещениям.

Отдельно отбрасывается **первый фрагмент, в который не поместился транспортный
заголовок**: правило с портами не может судить о пакете, у которого порт
намеренно унесён в следующий фрагмент, а получатель его соберёт. Ни один
настоящий стек таких фрагментов не шлёт. Обычные фрагментированные датаграммы
проходят как раньше и проверяются по адресу.

## Состояние соединений

Правила описывают, **кому разрешено начинать разговор**, а не каждый пакет по
отдельности. Когда пакет проходит проверку, поток запоминается, и обратное
направление того же потока пропускается без повторной проверки.

Без этого правило вроде `deny private` ломало бы проброс портов внутрь VM:
пир входящего SSH-соединения — это приватный адрес шлюза контейнера, и ответы
гостя выглядели бы как попытка самому полезть в домашнюю сеть.

Что из этого следует:

* поток может появиться только от пакета, который правила **уже разрешили**;
* TCP-поток забывается по `RST` и по часу простоя, UDP/ICMP — через 2 минуты;
* при изменении правил таблица потоков сбрасывается, поэтому ужесточение
  применяется и к уже открытым соединениям;
* пир, которому разрешили постучаться в проброшенный порт, получает право на
  ответный трафик. Если это нежелательно — ограничь входящие
  (`NET_ALLOW_IN` / `NET_POLICY_IN: deny`).

Отключается через `NET_GUARD_STATEFUL=N` — тогда каждый пакет проверяется
сам по себе.

---

## Что видит гость

По умолчанию (`NET_GUARD_REJECT=Y`) заблокированное соединение обрывается сразу:

* TCP → в гостя уходит `RST`, приложение получает «connection refused»;
* UDP/прочее → ICMP «communication administratively prohibited».

Это заметно приятнее таймаутов. Если нужно именно «чёрная дыра» —
`NET_GUARD_REJECT=N`.

## Файл правил и живое обновление

```yaml
environment:
  NET_RULES_FILE: /storage/net-rules.conf
volumes:
  - ./storage:/storage
```

```conf
# /storage/net-rules.conf
allow tcp:archive.ubuntu.com:80,443
allow tcp:registry-1.docker.io:443
allow udp:*:123          # NTP

deny  private            # никакой домашней сети
allow any                # остальной интернет можно
```

Файл перечитывается на лету — VM перезапускать не нужно. Правила применяются
только когда файл «устоялся» (не менялся один интервал опроса), поэтому
сохранение на середине редактирования не открывает доступ случайно.

Два случая специально **не** меняют политику:

* файл не парсится — остаётся работать предыдущая версия, в лог уходит ошибка;
* файл исчез — политика сохраняется.

Оба варианта иначе означали бы «правила молча расширились», а для контроля
доступа это худший из возможных отказов.

---

## Правила по именам хостов

`tcp:api.github.com:443` резолвится при старте и обновляется раз в
`NET_RESOLVE_INTERVAL`. Если резолвер временно недоступен, остаётся предыдущий
ответ.

Подходит для сервисов со стабильными адресами. Для CDN с большими пулами IP
надёжнее указывать сети провайдера, а не имя.

## Статус и отладка

```yaml
environment:
  NET_GUARD_HTTP: ":8010"
ports:
  - "127.0.0.1:8010:8010"
```

```bash
curl -s 'http://127.0.0.1:8010/?text=1'
```

```
uptime   1m0s
guest    172.17.0.2
gateway  172.17.0.1

egress (default deny)

frames   out=20 in=7
bytes    out=2381 in=1512
denied   out=2 in=0
rejects  tcp=2 icmp=0
flows    3 tracked

blocked flows
  out tcp  172.17.0.3 -> 18.238.136.44:443  x1  (default-deny)
  out tcp  172.17.0.3 -> 18.238.136.33:80  x1  (default-deny)
```

Эндпоинт только на чтение: правила через него менять нельзя, так что даже
случайно опубликованный порт не даёт расширить доступ VM.

Без эндпоинта заблокированные потоки всё равно видны в логах контейнера
(`docker compose logs`), по одной строке на поток — повторы схлопываются.

Проверить правила, не запуская VM:

```bash
docker run --rm -e NET_PRESET=internet -e NET_ALLOW="tcp:1.1.1.1:443" \
  --entrypoint vmguard ghcr.io/ophoperhpo/docker-vm-ubuntu-24.04:master -check
```

## Чего это не делает

* Не разбирает TLS и не фильтрует по доменам внутри соединения — решение
  принимается по адресу и порту.
* Не ограничивает скорость.
* Не заменяет изоляцию самой VM: гость по-прежнему может делать что угодно
  внутри разрешённых адресов.
* Работает только с `NETWORK=passt`. Для `tap`/`macvlan` фильтрация выполняется
  средствами хоста, и образ честно откажется стартовать вместо того, чтобы
  сделать вид, что правила действуют.
